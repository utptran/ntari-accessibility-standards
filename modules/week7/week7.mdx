2. Sanitization named attached of extension points using HTML fragments
The use HTML fragments deliberately keys each node as a slot name, and matches the external data (attribute data-ext) from the template to the user’s input for each node. Before the result is submitted, the node is sanitized against an allowlist, which can contain allowed tags and attributes. This prevents the injection of scripts, for example the literal use of the tag ‘script’.

Below is a code excerpt showing this example:

import DOMPurify from "dompurify";

const ALLOWED = { ALLOWED_TAGS: ["p", "a", "b", "i", "img"],
                  ALLOWED_ATTR: ["href", "src", "alt"] };

for (const [name, html] of Object.entries(fragments)) {
  const slot = document.querySelector(`[data-ext="${name}"]`);
  if (!slot) continue;                         // unknown slot name: ignore
  slot.innerHTML = DOMPurify.sanitize(html, ALLOWED);
}

This example follows the principle of separability, as it allows the user to edit their data (tags and attributes) while allowing the platform (web stack, such as DOMPurify) to sanitize the inputs.

3. Saved-at non-executable (non-opaque?) named meta-data
Meta-data is saved to track the publisher, fragment edited, CSS styling file, and when the edit was saved. It should be non-executable, as in parsed as plain data, to allow sanitization seen in the attachment points HTML fragments. One thing that stood out to me was the use of ‘non-opaque’. After some research, if found that opaque data means it can’t be manipulated (e.g., inspected or debugged). If the metadata is readable, then we can sanitize, compare saved versions in git, and migrate files when formatting changes.
